Organização de código e responsabilidades

Escrever software fácil de compreender, testar e modificar — sem complexidade desnecessária.

Objetivo da aula

Identificar responsabilidades misturadas e reorganizar uma funcionalidade em partes simples. Trabalhar coesão, acoplamento e separação de responsabilidades com um exemplo concreto, sem transformar a aula numa discussão de frameworks ou padrões complexos.

Mensagem central: organizar código não significa criar mais arquivos ou camadas por moda. Significa tornar cada parte mais compreensível, testável e fácil de modificar.

Revisão e conexão com a aula 05

Retome a função de desconto: ela recebe valores e devolve resultados. Por que não deveria também consultar banco, enviar e-mail e montar uma resposta HTTP? Convide a Jenny a identificar decisões que deveriam estar fora dessa função.

Três conceitos com linguagem prática

Responsabilidade

Qual problema este trecho resolve? Quem muda quando a regra muda?

Coesão

As operações de uma função ou módulo pertencem ao mesmo objetivo?

Acoplamento

Quanto esta parte depende de detalhes de outras partes?

Nem toda função comprida é errada, nem toda função curta é boa. O foco é a clareza das fronteiras e a facilidade de mudar regras sem efeitos colaterais.

Código inicial — tudo misturado

O exemplo é intencionalmente simplificado e simula persistência por uma lista. Peça que a Jenny destaque onde estão validação, cálculo, armazenamento e apresentação.

pedidos = []

def criar_pedido(cliente, subtotal):
    if not cliente:
        return {"erro": "Cliente obrigatório"}
    if subtotal < 0:
        return {"erro": "Subtotal inválido"}

    desconto = 0
    if subtotal >= 200:
        desconto = min(subtotal * 0.10, 50)

    total = subtotal - desconto
    pedido = {"cliente": cliente, "total": total}
    pedidos.append(pedido)
    print("Pedido criado:", pedido)
    return pedido
Questão: se a regra de desconto mudar, onde mexer? E se o banco for trocado por API? E se a interface precisar exibir a mensagem em outro idioma?

Uma refatoração possível

Dividir por papéis, sem criar uma classe para cada linha. Neste recorte didático usamos números simples para focar estrutura; em valores monetários reais, reaproveite Decimal da aula 05.

def validar_pedido(cliente, subtotal):
    if not cliente:
        raise ValueError("Cliente obrigatório")
    if subtotal < 0:
        raise ValueError("Subtotal inválido")

def calcular_desconto(subtotal):
    if subtotal < 200:
        return 0
    return min(subtotal * 0.10, 50)

def montar_pedido(cliente, subtotal):
    validar_pedido(cliente, subtotal)
    desconto = calcular_desconto(subtotal)
    return {"cliente": cliente, "total": subtotal - desconto}

def salvar_pedido(pedido, repositorio):
    repositorio.append(pedido)
    return pedido

pedidos = []
novo = montar_pedido("Jenny", 250)
salvar_pedido(novo, pedidos)
print(novo)

Atenção: esta não é “a única arquitetura correta”. Em um projeto maior, as responsabilidades podem virar módulos, serviços ou classes. Por enquanto, funções bem nomeadas tornam o fluxo mais claro.

Desenho de responsabilidades

Entrada / API→Validação→Regras de negócio→Persistência

Discuta onde se converte erro em status HTTP: a camada de entrada/entrega pode traduzir ValueError em uma resposta adequada; a função de cálculo não precisa conhecer HTTP. Diferencie dependência entre módulos de uma sequência normal de chamadas.

Exercício principal — refatorar sem quebrar comportamento

  1. Marque no código original o que é validação, regra, persistência e apresentação.
  2. Descreva por que vale a pena separar pelo menos duas dessas responsabilidades.
  3. Refatore o exemplo preservando os resultados para entradas válidas e a rejeição de entradas inválidas.
  4. Compare os resultados antes e depois para clientes vazios, subtotais negativos, 199,99, 200 e 700.
  5. Simule uma mudança na regra de desconto. Qual parte precisa mudar?
Critério de sucesso: a Jenny consegue apontar limites entre responsabilidades, refatorar uma função sem perder comportamento e explicar como a nova estrutura reduz o impacto de mudanças.

Perguntas para discussão

  • Separar tudo em arquivos diferentes torna o sistema automaticamente melhor?
  • Por que uma função de regra de negócio não deveria imprimir mensagens diretamente?
  • Como testar o cálculo do desconto sem precisar salvar no banco?
  • O que mudaria se a persistência fosse feita por uma API externa?
  • Que riscos aparecem quando refatoramos sem testes?
  • Qual seria um sinal de que dividimos o código demais?

Mini desafio entre encontros (30–60 min)

Reorganizar uma funcionalidade pequena da EloIs Store ou de um exemplo isolado. Entregar o “antes e depois” e um texto curto explicando duas decisões tomadas. Adicionar pelo menos três testes manuais ou automatizados para comprovar equivalência de comportamento.

Escopo: não refatorar a aplicação inteira e não mudar regras de negócio durante a reorganização. Deixe alterações de comportamento para um PR separado.

O que ela deve sair sabendo

  • Diferenciar validação, negócio, persistência e apresentação.
  • Explicar coesão e acoplamento usando exemplos próprios.
  • Identificar responsabilidades misturadas.
  • Refatorar uma função sem alterar comportamento esperado.
  • Justificar quando uma abstração ajuda e quando só cria complexidade.
