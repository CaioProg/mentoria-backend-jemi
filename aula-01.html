AULA 01 • FUNDAMENTOS

Como um backend funciona de ponta a ponta

O objetivo não é falar de framework. É criar um modelo mental do que acontece entre uma ação do usuário e a resposta do sistema.

1 horaDuração
MacroNível de abstração
LojaLaboratório prático

Objetivo da aula

Ao final, ela deve conseguir explicar, sem depender de código, o caminho percorrido por uma requisição e identificar a responsabilidade de cada parte.

Cliente→HTTP→API→ Regra de negócio→Banco / Integrações→Resposta

O que explicar

1

Cliente e servidor

O cliente inicia uma operação. O backend recebe uma requisição, toma decisões, acessa recursos e devolve uma resposta.

2

Request e response

Uma requisição carrega intenção e dados. A resposta comunica o resultado. O protocolo HTTP é o contrato de transporte mais comum em APIs web.

3

API não é a regra de negócio

O endpoint é uma porta de entrada. Regras como “não vender produto sem estoque” pertencem ao comportamento do sistema, não ao protocolo.

4

Persistência

O banco mantém estado durável. É uma boa oportunidade para diferenciar memória do processo, cache e persistência.

5

Integrações externas

Pagamento, e-mail, frete e outros serviços estão fora do controle direto da aplicação e introduzem latência e falhas.

6

Backend é coordenação

Muito do trabalho é coordenar regras, dados e sistemas externos de maneira previsível, segura e observável.

Roteiro sugerido para os 60 minutos

0–10 minPergunte como ela imagina que uma compra funciona hoje.

25–50 minFaçam juntos o fluxo “Finalizar compra”.
50–60 minPeça para ela recontar o fluxo e registre dúvidas.

Exercício principal — “Finalizar compra”

Comece apenas com:

Requisito: “O usuário possui itens no carrinho e clicou em Finalizar compra.”

Peça para ela construir a sequência antes de você completar. Um possível fluxo:

  1. O cliente envia a intenção de criar/finalizar um pedido.
  2. A API identifica e valida o usuário.
  3. O sistema busca ou recebe os itens envolvidos.
  4. Valida disponibilidade e regras de negócio.
  5. Calcula/prepara valores.
  6. Persiste o pedido.
  7. Aciona ou agenda o pagamento.
  8. Atualiza/reserva estoque conforme a estratégia adotada.
  9. Retorna uma resposta compreensível ao cliente.
Importante: não tente chegar à “arquitetura perfeita”. O objetivo é fazê-la perceber que uma ação simples na tela atravessa várias responsabilidades.

Perguntas para conduzir a conversa

  • Quem inicia a operação?
  • Que informações o backend precisa receber?
  • O backend deveria confiar no preço enviado pelo frontend?
  • Onde o preço real do produto deveria ser obtido?
  • O que precisa ser validado antes de criar o pedido?
  • O que acontece se o banco estiver indisponível?
  • E se o provedor de pagamento demorar 20 segundos?
  • Qual parte do fluxo pertence ao nosso sistema e qual pertence a terceiros?
  • Como um QA poderia descobrir em qual etapa a operação falhou?

Mini desafio

Sem escrever código: peça para ela desenhar o fluxo de “Consultar meus pedidos” e explicar o que muda em relação a “Finalizar compra”.

Você pode avaliar se ela percebe que a consulta tende a ser uma operação de leitura, envolve autenticação/autorização, consulta ao banco e transformação em resposta, mas não deveria produzir efeitos colaterais no domínio.

O que ela deve sair sabendo

  • Explicar cliente × servidor.
  • Explicar request × response.
  • Diferenciar API, regra de negócio e persistência.
  • Visualizar integrações externas como fontes de falha.
  • Seguir mentalmente uma operação de ponta a ponta.
