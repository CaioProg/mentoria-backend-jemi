Do requisito à implementação

Entender uma demanda e transformá-la em passos, código simples e resultados verificáveis.

Objetivo da aula

Converter uma regra de negócio em passos verificáveis e em uma função pequena e legível. Não é uma aula para decorar sintaxe: é para entender entradas, saídas, decisões e casos de borda.

Mensagem central: antes de escrever código, explique o problema em linguagem simples. Uma solução boa precisa atender às regras, ser testável e permitir mudanças.

Diagnóstico inicial (primeiros 10–15 minutos)

Sem IA e sem pressão de acertar tudo, peça à Jenny que leia o código abaixo e diga o resultado para cada entrada, identifique a condição e sugira um caso não previsto.

def frete_gratis(total):
    if total >= 150:
        return True
    return False

# O que acontece para 149, 150 e 180?
  • Ela entende parâmetro, retorno e condição?
  • Consegue diferenciar número, texto, booleano e uma lista de itens?
  • Consegue explicar o que aconteceria se o total fosse negativo?
Adaptação: se surgirem lacunas, retome funções, condicionais e tipos durante o exercício. Se estiver confortável, avance para decomposição e casos de teste. Não use o diagnóstico como prova ou nota.

Da demanda para uma especificação clara

Demanda: “A EloIs Store quer conceder 10% de desconto nos pedidos de pelo menos R$ 200, mas limitar o desconto a R$ 50. Pedidos abaixo de R$ 200 não recebem desconto.”
  1. Entrada: subtotal do pedido em reais (valor não negativo).
  2. Saída: valor do desconto e total final.
  3. Regras: desconto de 10% a partir de R$ 200, com teto de R$ 50.
  4. Casos de borda: subtotal 0, 199,99, 200, 500, 1000 e valores negativos.
  5. Fora de escopo: impostos, cupons, frete e persistência em banco.

Discuta o que “pelo menos R$ 200” significa, se o desconto é calculado antes do frete e quem aprova as regras ambíguas. Requisitos claros economizam retrabalho.

Decomposição: raciocinar antes de codificar

Entender a regra→Definir entradas→Separar decisões→Implementar→Validar

Peça que ela escreva primeiro o pseudocódigo: rejeitar valores negativos; se subtotal for menor que 200, desconto zero; caso contrário, calcular 10% e respeitar limite; subtrair e retornar.

Exemplo de referência (Python)

Mostre este exemplo somente depois de ela propor a própria solução. Em dinheiro real, valores decimais pedem cuidado: aqui usamos Decimal para evitar erros comuns de representação binária.

from decimal import Decimal, ROUND_HALF_UP

def calcular_total(subtotal: Decimal) -> tuple[Decimal, Decimal]:
    if subtotal < 0:
        raise ValueError("Subtotal não pode ser negativo")

    desconto = Decimal("0.00")
    if subtotal >= Decimal("200.00"):
        desconto = min(subtotal * Decimal("0.10"), Decimal("50.00"))

    desconto = desconto.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
    total = subtotal - desconto
    return desconto, total

print(calcular_total(Decimal("200.00")))
# (Decimal('20.00'), Decimal('180.00'))

Discussão: o que é responsabilidade desta função? Ela deveria buscar o pedido no banco, chamar uma API externa ou imprimir a resposta? Por quê?

Exercício principal — regra de desconto

  1. Reescreva a demanda com suas próprias palavras.
  2. Liste entradas, saídas e pelo menos cinco casos de teste.
  3. Crie uma função sem acesso ao banco ou interface.
  4. Execute casos de borda e valide o teto do desconto.
  5. Explique o que mudou entre a primeira versão e a versão revisada.
Critério de sucesso: a Jenny consegue explicar cada condição, prever o resultado de entradas conhecidas e justificar por que a lógica foi isolada em uma função.

Perguntas para discussão e QA

  • Qual a diferença entre requisito, regra de negócio e implementação?
  • O que fazer se a descrição disser “acima de R$ 200” em vez de “a partir de R$ 200”?
  • O desconto é R$ 50 para um subtotal de R$ 1000? Por quê?
  • O que acontece para um pedido de R$ 199,99?
  • Por que uma função que recebe dados é mais fácil de testar que uma que consulta a API?
  • Como você verificaria que uma mudança futura não quebrou os descontos antigos?

Mini desafio entre encontros (30–60 min)

Adicionar uma regra opcional para clientes VIP: o desconto passa a 15% para pedidos elegíveis, com o mesmo teto de R$ 50. Explicitar se a regra VIP substitui ou soma ao desconto normal (neste exercício, substitui).

Entregar a função e uma tabela com entradas/saídas esperadas. Não é necessário abrir PR na aplicação se isso exigir alterar fluxos em produção; um arquivo isolado é suficiente.

O que ela deve sair sabendo

  • Identificar o que falta esclarecer num requisito.
  • Decompor um problema em passos e escrever uma função pequena.
  • Usar condicionais, parâmetros e retornos para representar regras.
  • Considerar limites, entradas inválidas e validação.
  • Explicar o código produzido sem depender de IA.
