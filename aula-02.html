Objetivo da aula

Ao final, ela deve conseguir olhar para um requisito e propor um contrato HTTP razoável: recurso, método, rota, entrada, saída e status code — sabendo que existem escolhas e trade-offs.

Mensagem principal: uma API é um contrato entre sistemas. O objetivo não é decorar verbos; é comunicar corretamente a intenção da operação.

Conceitos essenciais

GET

Consultar

Recupera uma representação de um recurso. Em condições normais, não deve produzir mudanças de estado como efeito principal.

POST

Criar / executar

Normalmente usado para criar recursos ou iniciar operações que produzem efeitos.

PUT

Substituir

É associado à substituição da representação de um recurso e possui semântica idempotente.

PATCH

Alterar parcialmente

Expressa uma alteração parcial. A semântica exata depende do contrato definido pela API.

DELETE

Remover

Solicita a remoção de um recurso. No domínio, “cancelar” nem sempre significa apagar.

STATUS

Comunicar resultado

2xx sucesso, 4xx problema na requisição/estado percebido pelo cliente, 5xx falha no processamento do servidor.

Não comece pelos endpoints

Escolha primeiro os recursos do domínio que fazem sentido para quem consome a API.

Exercício — desenhando a API da loja

Peça para ela propor primeiro. Só depois compare com algo semelhante a:

GET    /products
GET    /products/{id}

GET    /cart
POST   /cart/items
PATCH  /cart/items/{itemId}
DELETE /cart/items/{itemId}

POST   /orders
GET    /orders
GET    /orders/{id}

POST   /orders/{id}/cancellation

A última rota é ótima para discussão: DELETE /orders/{id} representaria corretamente cancelar um pedido que precisa continuar existindo no histórico? Não necessariamente.

Status codes para discutir

200 OK

Operação realizada e resposta disponível.

201 Created

Um novo recurso foi criado com sucesso.

204 No Content

Sucesso sem necessidade de corpo na resposta.

400 Bad Request

A requisição não pode ser processada no formato/condições apresentadas.

401 / 403

Ótima discussão para separar autenticação de autorização.

404 Not Found

O recurso solicitado não foi encontrado conforme o contrato da API.

409 Conflict

Útil para conflitos de estado, como determinadas operações incompatíveis com o estado atual.

500 Internal Server Error

O servidor falhou ao processar uma requisição que chegou até ele.

Idempotência — introdução

Use o exemplo da compra:

Cenário: o usuário clicou três vezes em “Finalizar compra”. Devemos criar três pedidos?

Explique a ideia de que repetir uma operação idempotente deve produzir o mesmo efeito desejado no servidor. Não é preciso esgotar o tema aqui — ele voltará na aula de resiliência.

Questões úteis: existe um identificador da intenção de compra? O cliente pode enviar uma chave de idempotência? O banco pode ajudar a garantir unicidade? E se houver duas instâncias da API?

Perguntas para conduzir a aula

  • Qual é o recurso que estamos manipulando?
  • Estamos consultando ou produzindo um efeito?
  • O cliente precisa enviar um body?
  • Qual resposta seria útil para quem chamou?
  • Qual status code descreve melhor o resultado?
  • “Cancelar pedido” significa excluir o pedido?
  • O que aconteceria se a mesma requisição fosse enviada duas vezes?
  • Como um QA testaria o contrato sem conhecer a implementação?

Mini desafio

Dê a ela quatro requisitos: favoritar produto, alterar endereço de entrega, pagar pedido e consultar estoque. Peça rota, método, entrada, resposta e principais status codes.

O objetivo não é existir uma única resposta correta, mas ela conseguir justificar as decisões.

Materiais de apoio

MDN — HTTP Request Methods ↗ Referência direta para métodos HTTP e suas semânticas. MDN — HTTP Response Status Codes ↗ Referência para as famílias 1xx–5xx e códigos individuais. MDN — HTTP Headers ↗ Para mostrar como metadados acompanham requests e responses. Microsoft REST API Guidelines ↗ Material mais avançado para consultar boas práticas e decisões de design. RFC 9110 — HTTP Semantics ↗ Fonte normativa; útil como referência avançada, não como leitura obrigatória para a aula.
