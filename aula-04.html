Banco de dados e modelagem

Transformar regras e relações de negócio em tabelas, chaves, restrições e consultas consistentes.

Objetivo da aula

Ao final, a Jemi deve conseguir converter o modelo de domínio da aula 03 em um modelo relacional coerente, explicar chaves e relacionamentos, escolher restrições básicas e raciocinar sobre integridade e concorrência.

Mensagem principal: o banco não é só onde guardamos dados; ele é também uma última linha de proteção para a consistência. O modelo relacional é uma decisão de persistência — não precisa ser idêntico ao modelo de domínio.

Do desenho de domínio para as tabelas

Regras do negócio→Entidades e relações→Tabelas e chaves→Restrições

Utilize o mesmo exemplo da loja para definir tabelas iniciais. Não é preciso escrever código da API: o foco é descobrir como os dados se relacionam e o que o banco pode garantir.

produtos + estoques

Um produto tem um estoque nesta versão simplificada (relação 1:1). Com múltiplos depósitos, o modelo precisaria mudar.

pedidos + itens_pedido

Um pedido possui vários itens (1:N). Cada item aponta para um produto e registra preço e quantidade da compra.

pedidos + pagamentos

Um pedido pode ter várias tentativas de pagamento (1:N), mas as regras precisam evitar cobranças em duplicidade.

clientes + pedidos

Um cliente pode fazer vários pedidos (1:N). A ligação ajuda a consultar pedidos de uma pessoa, sem substituir regras de autorização.

Restrições importantes: o que cada uma protege?

PRIMARY KEY

Identidade da linha

Evita chaves duplicadas ou nulas. Ex.: pedidos.id.

FOREIGN KEY

Referência válida

Impede item de apontar para pedido ou produto inexistente, respeitando a política de exclusão escolhida.

NOT NULL

Campo obrigatório

Exige que uma informação esteja preenchida; não garante que o texto faça sentido.

UNIQUE

Unicidade

Evita dois produtos com o mesmo SKU; pode proteger uma chave de idempotência.

CHECK

Regra local

Impede quantidade negativa ou estado fora do conjunto permitido, se expresso no esquema.

INDEX

Acesso eficiente

Ajuda consultas específicas, mas aumenta espaço e custo de escrita. Não substitui restrições de integridade.

Discussão: CHECK (disponivel >= 0) impede valores negativos, mas, sozinho, não define toda a estratégia para duas compras simultâneas.

Modelo físico ilustrativo (PostgreSQL)

Este é um recorte didático do esquema, não um script completo de produção. Ele mostra PK, FK, restrições e um preço histórico por item.

CREATE TABLE produtos (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku TEXT NOT NULL UNIQUE,
  nome TEXT NOT NULL,
  preco_atual NUMERIC(12,2) NOT NULL CHECK (preco_atual >= 0)
);

CREATE TABLE estoques (
  produto_id BIGINT PRIMARY KEY REFERENCES produtos(id),
  disponivel INT NOT NULL CHECK (disponivel >= 0),
  reservado INT NOT NULL DEFAULT 0 CHECK (reservado >= 0)
);

CREATE TABLE pedidos (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  cliente_id BIGINT NOT NULL, -- FK para clientes no modelo completo
  status TEXT NOT NULL CHECK
    (status IN ('CRIADO','AGUARDANDO_PAGAMENTO',
                'PAGO','CONCLUIDO','CANCELADO')),
  criado_em TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE itens_pedido (
  pedido_id BIGINT NOT NULL REFERENCES pedidos(id),
  produto_id BIGINT NOT NULL REFERENCES produtos(id),
  quantidade INT NOT NULL CHECK (quantidade > 0),
  preco_unitario NUMERIC(12,2) NOT NULL CHECK (preco_unitario >= 0),
  PRIMARY KEY (pedido_id, produto_id)
);

CREATE TABLE pagamentos (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  pedido_id BIGINT NOT NULL REFERENCES pedidos(id),
  status TEXT NOT NULL,
  referencia_externa TEXT UNIQUE
);

Escolhas conscientes: o preço do item é um snapshot histórico; a chave composta de itens_pedido pressupõe que cada produto aparece uma única vez por pedido; caso existam variações ou linhas repetidas, considere um ID próprio de item.

Normalização sem perder o histórico

Não copie nome, preço atual e descrição do produto em todas as tabelas sem motivo. Centralizar os dados do catálogo evita inconsistências quando a mesma informação muda.

Por outro lado, preço unitário no momento da compra pertence ao histórico do pedido. Guardá-lo em itens_pedido é uma decisão intencional de domínio, não um erro a ser “corrigido” com um JOIN no preço atual.

Pergunte: se o nome de um produto mudar, o comprovante antigo deve exibir o nome de hoje ou o nome daquela compra? Isso abre a discussão sobre snapshots de descrição, impostos e descontos sem sobrecarregar o primeiro modelo.

Consulta, JOIN e índice

Uma pergunta prática: “Quero ver os últimos pedidos de um cliente”. O SQL pode relacionar dados por chaves; o índice depende das consultas reais.

SELECT id, status, criado_em
FROM pedidos
WHERE cliente_id = $1
ORDER BY criado_em DESC
LIMIT 20;

CREATE INDEX idx_pedidos_cliente_criado
  ON pedidos (cliente_id, criado_em DESC);

Explique que FOREIGN KEY garante vínculo, mas em PostgreSQL não cria automaticamente índice na coluna que referencia outra tabela. Índices extras devem ser escolhidos após observar filtros, ordenações e volume.

Não antecipe otimização: na próxima aula vocês estudarão scans, joins, índices e planos de execução com mais profundidade. Hoje basta compreender por que uma consulta encontra linhas relacionadas.

Transação e duas compras da última unidade

A aplicação leu “1 disponível”; dois clientes tentam reservar ao mesmo tempo. Duas verificações em memória não são garantia suficiente. Uma forma de demonstrar a concorrência no banco é a atualização condicional:

UPDATE estoques
SET disponivel = disponivel - $2,
    reservado = reservado + $2
WHERE produto_id = $1 AND disponivel >= $2
RETURNING produto_id;

Com dois pedidos concorrentes de uma unidade e somente uma disponível, a condição impede que ambos reduzam o estoque. Se a consulta não retornar linha, a reserva não aconteceu. A atualização e o registro da reserva/pedido precisam ser coordenados em uma transação consistente.

Atenção: não mantenha uma transação de banco aberta aguardando uma API de pagamento. Integrar sistemas externos exige fluxos de confirmação, expiração ou compensação tratados explicitamente.

Exercício principal — transformar o domínio em dados

Requisito: “Um cliente pode realizar pedidos com vários produtos, cada compra mantém o preço original e várias tentativas de pagamento podem ocorrer sem apagar o histórico.”
  1. Desenhe clientes, produtos, estoques, pedidos, itens_pedido, pagamentos e suas cardinalidades.
  2. Defina PK e FK. Discuta se a ligação Produto–Estoque é 1:1 ou 1:N.
  3. Escolha pelo menos três restrições: quantidade positiva, SKU único, referências válidas etc.
  4. Explique como consultar os pedidos de um cliente e seus itens usando JOIN.
  5. Descreva o que acontece quando duas compras disputam a última unidade.
Critério de sucesso: ela sabe dizer que tipo de inconsistência cada chave ou restrição evita e consegue distinguir o que o banco garante do que precisa ser coordenado pela aplicação.

Perguntas de QA: testes para o banco

  • É possível gravar um item_pedido para um pedido inexistente?
  • Dá para cadastrar dois produtos com o mesmo SKU?
  • O banco aceita quantidade = -1 ou disponivel = -5?
  • Se um produto for removido, o histórico de pedidos fica íntegro? Seria melhor inativá-lo?
  • Se o preço atual mudar, o valor histórico do pedido permanece igual?
  • O que ocorre quando duas transações reservam o último item ao mesmo tempo?
  • Um pagamento pode ser inserido duas vezes com a mesma referência externa?
  • Como descobrir a causa quando um INSERT falha por FK, UNIQUE ou CHECK?

Mini desafio

Sem usar ORM: desenhe uma consulta que retorne pedido, data, produto, quantidade e preço histórico. Depois pergunte qual índice poderia ajudar a listagem frequente de pedidos recentes de um cliente.

Estimule o raciocínio, não a memorização da sintaxe. Se a Jemi quiser, valide as hipóteses em um banco de testes com poucos dados e depois com dados suficientes para observar diferença de plano.

O que ela deve sair sabendo

  • Explicar PK, FK, UNIQUE, NOT NULL e CHECK com exemplos.
  • Desenhar relações 1:1 e 1:N, e justificar quando seria N:N.
  • Distinguir normalização de snapshots históricos intencionais.
  • Entender a ideia de transação e atualização condicional sob concorrência.
  • Relacionar consulta, JOIN e índice sem confundir performance com integridade.
